The Busyboard Domain

Buttons, lamps, and wiring the robot never sees

pybullet_busyboard - branch busyboard-experiments
Assets: docs/envs/busyboard/

Why another domain?

  • Every other domain in the suite hides numbers: fan wind, boil heat, glue cure time, domino friction. The shape of the hidden process is known and a few knobs are fitted.
  • Busyboard hides structure: which button feeds which lamp. No setting of a continuous parameter vector expresses it.
  • Some lamps need two buttons at once (an interlock). Earlier busyboard benchmarks for robot learning left that out on purpose to keep the board easy to read from random play.
  • Evidence arrives late: a lamp only lights after its buttons have been held for a while, so the button pressed most recently is often not the one that caused the light.
  • Some buttons do nothing, and every goal asks for some lamp to stay dark. "Press everything" is therefore not a strategy.

The world

  • A Panda arm faces a children's busy board sunk flush into the table.
  • Buttons (front): toggle switches. Pushed from one side they latch on, from the other off. The pale slider's position is the button's state.
  • Lamps (back): grey blocks that turn amber as they light. The robot never touches them.
  • Three buttons fit in one row. Bigger boards get a second row of buttons.
  • The only things the robot can do: press a button, release a button, or wait.

What the board hides

  • Each lamp has a drive condition: either one button ("b2") or two buttons that must both be on ("b0 & b2").
  • While the condition holds, a hidden charge builds up. When it stops holding, the charge drains, faster than it built.
  • What the camera sees is brightness. It stays at exactly zero for the first ~60% of the charge and only then ramps up. A lamp that is half-way to lighting looks identical to a dead one.
  • Example: the four-button, three-lamp board used in all the videos.

  • So the gap between cause and visible effect is roughly two button operations. Press A, then press B, and the lamp lights during B.
  • Undoing is cheap: release a button and its lamp is dark before the next press finishes.
  • Waiting is a real action. A lamp only lights while the board is left alone in a driving configuration.

Goals: light these, keep those dark

  • Every board starts fully off: all buttons released, all lamps dark and uncharged.
  • A goal is a lit/dark assignment over the lamps, e.g. "Use the buttons to leave lamp0, lamp2 lit and lamp1 dark."
  • Goals are drawn only from assignments that some button setting exactly realizes, so every task is solvable.
  • With two or more lamps, at least one lamp must stay dark. That off-target is the whole point.

Latch everything and wait. Lights lamp0, lamp1 and lamp2. lamp1 was supposed to stay dark, so the task fails.

State, predicates, skills

Objects and features

  • robot: x, y, z, fingers, roll, tilt, wrist
  • button: x, y, z, rot, is_on
  • lamp: x, y, z, rot, brightness (+ charge only when fully observable)

Predicates (all visible to the agent)

  • ButtonOn(b), ButtonOff(b)
  • LampOn(l), LampOff(l): brightness ≥ 0.5
  • HandEmpty(r)

Skills (shared factories, no board-specific motion code)

  • PressButton(r, b): push the slider to the on side
  • ReleaseButton(r, b): push it back
  • Wait(r): hold still

Partially observable run (--partially_observable True)

  • The charge feature is dropped. The agent sees only brightness and has to postulate the accumulator itself.
  • Same shape as boil's hidden heat behind bubbling_level, but here the latent sits behind an unknown wiring.

Train / test split

ButtonsLampsConditions per lampSetting
Train326busyboard_num_{buttons,lamps}_train
Test4 or 52 or 310 or 15busyboard_num_{buttons,lamps}_test
  • Test boards are bigger than anything seen in training. The intent: the rule (a conjunctive drive feeding a delayed accumulator) transfers, the bindings do not.
  • One wiring per seed (busyboard_fixed_wiring = True), sampled over the largest board (5 buttons, 3 lamps), then projected onto smaller boards: keep the first lamps, reduce button indices modulo the button count.
  • Half the lamps get an interlock on average (busyboard_interlock_prob = 0.5). Two lamps are never wired identically, so every lamp can be told apart by some experiment.
  • Board images: init_3buttons_2lamps.png (train size), init_4buttons_2lamps.png, init_4buttons_3lamps.png (test sizes).

  • The modulo projection changes lamp0's condition on every test board. A model that memorised "lamp0 needs b1 and b2" is wrong at test time.
  • Checked for seeds 0-4: in 5 of 5 seeds the train wiring of lamps 0-1 differs from every test board's.
  • This is by design (the domain motivates per-episode structure re-identification), but see the readiness slide for what it means for the current agent.

How much is there to find out?

  • Per lamp, the candidate conditions are: any single button, or any unordered pair.

  • Small enough to enumerate exactly, so information gain per experiment can be scored in bits against an optimal splitter.
  • A conjunction is symmetric: "b0 and b2" and "b2 and b0" are one hypothesis, not two.
  • The useful experiments are the ones that hold a configuration still long enough for the ramp to show. Covering every button once is not enough; the interlock and the delay both confound it.

The oracle: how the demonstrator plans

  • Pressing a button has no fixed effect, so a STRIPS operator cannot describe it. The oracle uses processes instead.
  • Two helper predicates, given to oracle approaches only: SoleDriver(b, l) and JointDrivers(b1, b2, l). They reconstruct the wiring from the board size, so the planner and the env cannot drift apart.
  • Exogenous processes: LightLampSole, LightLampJoint (condition: all drive buttons on, held for the delay), plus the matching darkening processes.
  • Endogenous: PressButton, ReleaseButton, Wait.
  • Result: 10/10 test tasks with oracle_process_planning and --sesame_check_expected_atoms False.

Goal: lamp0 and lamp2 lit, lamp1 dark. Plan: press button0, button2, button3, then wait.

  • The visibility contract is structural: the base file carries geometry and button mechanics and nothing else. Wiring, charge law, task distribution and goal thresholds live only in the subclass, which the agent never reads.
  • The true wiring is recorded in each task's offline_task_metrics, an experimenter-only channel, so runs can score how much of the wiring an agent actually recovered.

Is it ready to run? What to expect

  • Ready: env tests pass (7/7), oracle solves 10/10, config wired into envs/all.yaml and exp_busyboard.yaml, cherry-picked onto the current harness.
  • Oracle hybrid-sim arm (agent_oracle_hybrid_sim): should solve. Its params carry the max-board wiring and project it onto any board, and it has already captured a Wait-based 5-step plan end to end.
  • Learning arms (sim_predicator, agent_sim_learning): expect test failures under the current split. The agent learns bindings on 3-button boards, and those bindings are wrong on every test board in 5/5 seeds.
  • Test-time attempts run against the agent's own simulator, not the real board, so a wrong wiring is never corrected before the one real execution.
  • The continuous fitter cannot help either: the wiring params are rounded reals, a staircase with zero gradient almost everywhere.

Options: (a) evaluate on train-sized boards to measure model learning in isolation; (b) project by extension (new buttons and lamps added, old bindings kept) so training transfers partially; (c) keep the split and add test-time structure re-identification, which is the setting this domain was written to motivate.
